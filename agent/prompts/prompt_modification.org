The implemenation of ~solveDynNetwork()~ needs to be modified a bit, as it should
reflect the higher-level logic I try to clarify below.

- The point with terminating triggers is to stop integration whenever network
  topology will change.
- In that respect, there are only three trap states that are truly relevant:
  FULL, TRANSITORY (or "ACCUMULATING", though that name is misleading as water
  content may as well be decreasing as increasing) and EMPTY.  Whether a trap is
  "stagnant" or not is not really interesting, though the ~solveDynNetwork~
  function needs to be able to terminate if there are no more evolving traps in
  the network.
- For ~solveDynNetwork~ to make an initial distinction between full, transitory
  and empty traps upon calling:
  - an EMPTY trap is recognized by having a water content V===0  (exactly equal
    to zero)
  - a FULL trap is recognized by having a water content V===C, where C is the
    trap's capacity  (here, there's an unclarity whether the tstruct's trap
    capacity or the corresponding TrapGeometry's capacity is the one to compare
    against - whatever is chosen must be consistent and documented.
  - a trap that is neither EMPTY nor FULL is transitory.
- For ~solveDynNetwork()~, it is the _caller's_ responsibility to provide a
  valid network.  ~solveDynNetwork()~ should check this before doing any further
  work, and throw an error if the contract is unfulfilled.  The contract for a
  valid network is:
  - any FULL trap should have designated a spill path (DynFlowPath) out of it.
  - no TRANSITORY trap should have a spill path out of it (since it is not
    spilling)
  - the only EMPTY traps allowed in the network are lowest-level traps
    (according to tstruct).  If the trap has subtraps AND is EMPTY, it should
    not be present in the network - instead the relevant subtrap should be (if
    ~setup_network()~ is correct, this should have been taken care of when
    network was constructed).

- The state transitions that may occur for a trap are:
  - FULL -> TRANSITORY (if a trap with status FULL has a net negative inflow
    (whatever flows in less whatever is abstracted through infiltration and
    culverts)
  - TRANSITORY -> FULL (if water content of a trap reaches/surpasses the trap's
    capacity during integration.
  - TRANSITORY -> EMPTY (if water content reaches zero during integration - and
    only interesting for traps with subtraps)
  - Note that the event EMPTY -> TRANSITORY is never interesting, since the only
    traps that may ever be EMPTY in a valid network are lowest-level traps (no
    children), and for those, there is no topology change associated with the
    transitions between EMPTY/TRANSITORY.

- After having verified that the network passed as argument is indeed valid,
  ~solveDynNetwork~ will check if there are already occurrences of
  FULL->TRANSITORY from the start.  If so, it will return a special object that
  flags these to the caller, so the caller may take note.
- NB: General note: do not play around with infinitesimals or small tolerances
  inside ~solveDynNetwork()~ to "flag" changes in a trap's status.  Just report
  status changes to user and let it be handled outside.
- If network is valid and there are no immediate incidences of
  FULL->TRANSITORY, the actual integration may start, until an event is
  triggered, or until it is recognized that the system will not further evolve.
- The _caller_ should keep track of which traps are currently full/empty and
  reflect this when sending a network along with its state to ~solveDynNetwork~.

- The logic discussed here aims to be closely aligned with the logic used by the
  ~fill_sequence()~ function and associated machinery.  In time, the plan is
  that the network code should be closely integrated with ~fill_sequence()~ to
  handle those trap systems (including culverts, NBS, etc.) that cannot be
  purely predicted by the fixed rates that ~fill_sequence()~ currently assumes.
  Therefore, if you see any obvious inconsistencies between the logic described
  above and the corresponding logic in ~fill_sequence()~, report it before doing
  any further planning or implementation, so we can discuss how to reconcile it.

** DONE Q1: Simultaneous fills — who detects them?

*Claude's question:* The ODE callback fires for one trap at a time.  If traps A
and B both hit capacity in the same ODE step, ~solveDynNetwork~ returns ~:fill~
for A, with ~state[B] ≈ C_B~ (within ODE error, but not exactly C_B).  The
caller receives a state where B is not yet FULL by the exact-equality
definition — but B will fill "instantaneously" on the very next call.

Two options: (a) caller scans ~state~ for any ~V >= C~ after each event and
clamps those to exactly C; (b) ~solveDynNetwork~ returns all simultaneously
filled traps at once (changes return type).

*User answer:* The _caller_ is responsible to keep track of which traps are
considered filled or not.  The caller may want to update only the single trap
that was identified as newly FILLed.  If so, the caller should make sure that
any trap not yet "logically" filled should have a state consistent with their
status (i.e. not _exactly_ equal to trap capacity).  As such, the trap that was
simultaneously filled but not reported will be the next one to trigger as it
will fill up practically instantly.

More concretely: after registering A as full, the caller sends
~min(V_i, C_i - epsilon)~ for all other traps not yet registered as full.  This
ensures B (which overshot to V_B ≈ C_B or V_B > C_B) is sent as TRANSITORY on
the next call and fires ~:fill~ immediately.  Option (a) — no return type
change.

*Claude's response:* Agreed.  In Julia, ~prevfloat(C_i)~ is the right
"C minus one ULP" — no magic constant needed, and it is the largest float
strictly less than C.  Resolved.

** DONE Q4: Exactly what the caller does after each event

*Claude's question:* Does a ~:fill~ event trigger a topology rebuild (option a),
or is the same network reused (option b)?

*User answer:* Option (a) — topology rebuild after every fill.  The caller:
1. Updates its own record of filled traps.
2. Calls ~setup_network~ to rebuild network topology.
3. Ensures the filled trap has state set to exactly the trap's capacity; any
   non-filled trap has state lower than capacity (even if only by epsilon).

*Claude's follow-up for unspill:* After a FULL→TRANSITORY (~:unspill~) event,
the returned state has ~state[T] = C[T]~ (detected at t=0).  Passing ~C[T]~
again on the next call would classify T as FULL again (infinite loop).

*User answer (option b for unspill):* After an ~:unspill~ event, the trap is no
longer considered FULL but TRANSITORY.  The caller is responsible for setting
its state to something infinitesimally smaller than full capacity upon the next
call.  Concretely: ~prevfloat(C[T])~.  Resolved.

** DONE Q5: Reduced-dimensional ODE — can FULL traps be safely excluded?

*Claude's question:* If the ODE state vector contains only TRANSITORY traps, is
this compatible with detecting FULL→TRANSITORY transitions?

*User concern:* The only reason a FULL trap may stay full could be that it is
being constantly supplied by the outlet of a culvert from a different
(TRANSITORY) trap.  But this supply is nonconstant, and at some point this
could trigger an unspill event.  Also, NBS systems may introduce other
nonconstant rates.

*Claude's first response (incorrect):* Argued that with downhill culverts,
FULL trap stability increases as the downstream TRANSITORY trap fills.

*User rebuttal:* The upstream TRANSITORY trap Y might not be filling but
*emptying*.  As Y drains, the culvert supply from Y to FULL trap X diminishes.
At some point X's net inflow goes negative and it should unspill — a
FULL→TRANSITORY transition that happens mid-integration, not at t=0.

*Claude's revised response:* The user is correct.  The earlier argument only
considered TRANSITORY traps filling; but a trap Y can have net negative rate
(drain > inflow) and be emptying during integration.  In that case:
- Y→X downhill culvert: as Y empties, h_Y drops → culvert head h_Y − h_X
  decreases → culvert inflow to X decreases → X's net inflow decreases
- If X's net inflow crosses zero mid-integration: FULL→TRANSITORY for X occurs
  during the solve, not at t=0

The t=0 check alone is therefore insufficient.  The correct solution is to add
*unspill callback conditions* for each FULL trap, monitoring their net inflow as
a function of the TRANSITORY trap state vector ~u~.  Since FULL trap levels are
fixed at their capacity for the duration of a call, their net inflow is a pure
function of ~u_transitory~.  A ~VectorContinuousCallback~ entry can monitor
this: ~condition_unspill_X(u, t, integrator) = net_inflow_X(u)~, firing when
the value crosses zero from positive to negative.  This detects FULL→TRANSITORY
at any point during integration without needing FULL traps in the ODE state
vector.

The reduced-dimensional ODE architecture (state vector = TRANSITORY traps only)
is preserved; unspill callbacks are added as extra conditions on FULL traps.

requires the rate function logic to be callable with the partial state.  Is it

*** DONE Claude's response
Agreed — Option B is simpler and the right choice.  No counterargument.

One implementation detail that must be recorded: the ODE solver evaluates
intermediate Runge-Kutta stages, and for a FULL trap starting at exactly
V = C, those stages can produce V > C (overshoot into physically impossible
territory).  The rate function must guard against this by using
~min(V_j, C_j)~ when deriving the water-level ~h_j~ from volume for a FULL
trap.  This is the only clamp needed, and it is physically justified (the trap
cannot hold more than capacity).  It is NOT the same as the old ~abstol~ drift
hack — it is a hard physical boundary.

With that guard in place:
- When net_inflow_X >= 0: rate function gives dV_X = 0; V_X stays at C_X.
- When net_inflow_X < 0 (mid-integration, after Y has drained enough): rate
  function gives dV_X = net_inflow_X < 0; V_X begins to drop below C_X.
- Callback ~C_X - V_X~ crosses from 0 to positive → FULL→TRANSITORY event
  fires.

The t=0 check is still useful as a fast path (avoids starting the ODE when a
FULL trap is already draining), but the callback makes it no longer the *only*
detection mechanism.  Resolved.
